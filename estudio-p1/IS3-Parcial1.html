Unidad 1 · Sommerville + Git

Gestión de la configuración

La CM es el conjunto de políticas, herramientas y procesos para administrar los cambios del software. Permite saber, para cada versión del sistema, qué versión de cada componente la forma. Es un proceso del ciclo de vida (ISO/IEC/IEEE 12207). El VCS es la base: sin él no hay historia confiable, trabajo en paralelo, build automatizado, CI/CD ni rollback.

EjemploEl banco pide que el PDF del resumen lleve el CBU. Eso no es un commit improvisado: es un change request. Se estima que toca el generador y la plantilla, se aprueba, se versiona, y el release 2.4.1 documenta que el cliente lo recibió el 22/09.

Las cuatro actividades

Control de versiones. Seguimiento de cada componente y aislamiento del trabajo paralelo.

Build. Ensamblar código, datos y librerías en un ejecutable, con un comando repetible. El script de build es parte del producto.

Release management. Qué versión se entrega, a qué cliente, en qué fecha y con qué documentación. Sirve para reconstruir lo que ese cliente tiene.

Administración del cambio. Todo cambio nace como propuesta. Se evalúan impacto, esfuerzo, riesgo y valor. Un Change Control Board, o el equivalente ágil, aprueba o rechaza. Después se implementa, se prueba y se libera. En ágil se automatiza la mecánica; la decisión de impacto no desaparece.

TrampaOptimizar un algoritmo interno no es CM. Tampoco diseñar la base ni escribir un test. El simulacro pregunta exactamente eso: la opción que no es CM es la optimización de algoritmos.

Codeline, snapshot, version, baseline, tag

Una codeline es la secuencia de revisiones de un conjunto de archivos por un camino de desarrollo. main es una. release/2.3 es otra, con historial propio.

Un snapshot es una captura informal: un hash o un timestamp. Sirve para probar o para backup. No se distribuye.

Una version es un snapshot aprobado, estable, con número (1.2.3) y destinado a usuarios. Toda version fue snapshot. No todo snapshot llega a version.

Una baseline es la versión aprobada del conjunto completo: código, librerías, configuración del entorno y documentación. No se modifica. Es el punto desde el cual nace la versión siguiente, y es lo que necesitás para recrear el bug del cliente que tiene la 1.2.3.

Un tag es una etiqueta inmutable que apunta a un commit. v1.2.3 no se mueve. Marca el release, el punto de un hotfix y el rollback: “volvamos a v2.3.0”.

El repositorio guarda todas las versiones. El workspace es el directorio donde editás. El VCS sincroniza ambos.

Tres formas de resolver un conflicto

Locking, pesimista. El archivo nace read-only. Para editar pedís un lock exclusivo y el otro espera. Bloquea el trabajo paralelo. Sirvió en SCCS y RCS. Para código está obsoleto. Sigue teniendo sentido en binarios que no se pueden mergear, como un PSD.

Merge-before-commit. Cualquiera edita. Al commitear, el servidor mira si alguien subió antes. Si sí, rechaza el commit hasta que integres. Es el modelo de SVN. Los conflictos son raros si se integra seguido.

Commit-before-merge. El de Git. El commit local nunca se bloquea. Si al hacer push el remoto avanzó, tu historia divergió y mergeás o rebaseás cuando decidís. Eso habilita forks y pull requests.

Ana y BrunoLos dos editan Precio.cs. Ana pushea primero. En SVN, el commit de Bruno rebota hasta que actualice. En Git, el commit de Bruno ya existe en su máquina; lo que falla es el push.

Atomicidad y tres generaciones

SCCS y RCS versionaban por archivo. Un cambio de tres archivos eran tres historias. SVN y Git versionan por conjunto: un commit agrupa una intención, con un mensaje, y se puede revertir o hacer cherry-pick. Regla: un commit, una intención. “Arreglo el descuento y de paso renombro diez clases” mezcla dos cambios y ensucia el revert.

  1. SCCS (1972) y RCS (1982). Locking, por archivo, sin red. RCS guarda deltas invertidos: la última versión se lee rápido.
  2. CVS (1990) y SVN (2000). Cliente-servidor. CVS ya usa merge-before-commit pero sigue por archivo. SVN agrega commits atómicos y sigue centralizado.
  3. Git y Mercurial (2005). Distribuido, commit-before-merge, atómico. Linus lo escribió en dos semanas porque BitKeeper dejó de ser gratis. El kernel necesitaba velocidad, historia distribuida, ramas no lineales e integridad.

Modelo de objetos y las tres áreas

Todo objeto se identifica con un SHA-1. El contenido manda: el mismo contenido, el mismo hash.

  • Blob: el contenido de un archivo, sin nombre.
  • Tree: un directorio. Apunta a blobs y a otros trees, y ahí está el nombre.
  • Commit: apunta a un tree raíz, guarda autor, mensaje y uno o más padres.
  • Tag: apunta a un commit con un nombre inmutable. El anotado además tiene mensaje y autor.

Es un árbol de Merkle. El hash del commit incluye el hash del tree y el de sus padres. Cambiar un archivo del pasado cambia el blob, el tree y todos los commits posteriores.

Una rama es un puntero a un commit. Crearla es escribir 41 bytes. HEAD apunta a la rama activa. Cada commit nuevo mueve ese puntero. En SVN una rama era una copia cara, y por eso se usaban poco.

Las tres áreas: working directory (lo que editás), staging / index (lo que va a entrar en el próximo commit; git add), repository (.git; git commit). git fetch trae sin integrar. git pull es fetch más merge, o rebase. git push publica.

Merge contra rebase

main está en M3. Tu rama tiene A y B, salidos de M2.

Merge crea M4 con dos padres: M3 y B. La historia queda como ocurrió. No reescribe nada. El grafo se llena de commits de merge. Es lo correcto para integrar hacia main, porque el resto del equipo ya tiene esos commits.

Rebase reaplica A y B encima de M3. Nacen A' y B', con hashes nuevos. La historia queda lineal y git bisect se lee mejor. Si alguien había pulleado A, su historia ya no coincide.

ReglaRebase para mantener tu feature al día. Merge para integrar a main. Nunca rebase de una rama que otros usan.

Los cuatro branching models

Un branching model es la convención de cómo se organizan las ramas para desarrollar en paralelo, integrar, mantener versiones estables y desplegar. No hay uno mejor: depende de la madurez del equipo, la frecuencia de release, el tipo de producto y la regulación. Cambiarlo después sale caro.

GitFlow (Vincent Driessen, 2010)

Para releases planificados. Permanentes: main (lo que está en producción; cada commit es un release) y develop (integración del próximo release). Temporales: feature/* nace y vuelve a develop; release/x.y.z nace de develop cuando se congela el release, solo acepta bugfixes, y se mergea a main (con tag) y a develop; hotfix/* nace de main y vuelve a main (con tag) y a develop.

Sí: producto estable, varias versiones vivas, muchos juniors, QA formal de staging. No: startup que despliega varias veces por día, equipo senior con CI/CD estricto.

Trampadevelop no se crea al empezar el release ni se borra al final. Eso es release/x.y.z.

GitHub Flow

main siempre desplegable. Solo dos tipos de rama: main y features cortas. Flujo: branch, commits, pull request, review más CI, merge, deploy automático. No hay develop, ni release, ni hotfix formal. El hotfix es otra feature corta. Exige tests sólidos, code review, pipeline y rollback rápido. Sí para SaaS. No para varias versiones instaladas en clientes distintos, ni para un equipo sin tests.

Trunk-Based Development

Todos integran a una sola rama, en horas o como máximo un par de días. El trunk está siempre desplegable. Es lo que correlaciona con los equipos elite de DORA. El código incompleto entra detrás de un feature flag: apagado por defecto, se enciende para el equipo, después para un 1 %, después para todos. Si falla, se apaga el flag sin revertir el commit. El costo es deuda: los flags viejos hay que borrarlos.

Sí: equipo senior, CI maduro, monitoreo, SaaS de iteración rápida. No: equipo sin experiencia, software embebido o un videojuego que se publica como un disco, regulación que exige aprobación formal de cada release.

GitLab Flow

El intermedio. Por entorno: main → staging → production; cada merge despliega a ese ambiente y producción puede exigir aprobación. Por versión: release/2.0 y release/3.0 viven en paralelo; lo general entra a main y se cherry-pickea. Sirve en enterprise. Se vuelve un lío si nadie escribe las reglas.

Checkpoint

¿Por qué el rebase de una rama compartida es peligroso?

Porque reescribe los hashes. Quien ya tenía esos commits queda con una historia que no coincide. Rebase es para la feature local; hacia main se mergea.

Una feature de pagos va a tardar dos semanas y el equipo despliega todos los días. ¿Qué modelo y qué mecanismo?

Trunk-based o GitHub Flow, no GitFlow. El código incompleto entra detrás de un feature flag, apagado en producción.

Unidad 2 · sin orquestación

Sistemas distribuidos

Tanenbaum: un conjunto de computadoras independientes que aparecen ante el usuario como una sola. Operativamente: varios procesos, en nodos distintos, que solo se comunican por mensajes, comparten un objetivo y ofrecen una vista unificada. Si comparten memoria, no es distribuido. Si no colaboran, es una colección de servidores.

Se distribuye por tres motivos: escalar más allá de una máquina, seguir disponible si un nodo cae, y acercar el dato al usuario. Un servidor en Buenos Aires le cobra unos 200 ms de ida y vuelta a alguien en España antes de procesar nada.

Transparencias que el usuario no debería notar: de acceso, de ubicación, de replicación, de concurrencia y de fallo. Características deseables: escalabilidad, alta disponibilidad, tolerancia a fallos, elasticidad, consistencia, baja latencia, mantenibilidad y observabilidad.

Centralizado y SPOF

Un solo servidor con la base al lado es el MVP correcto: modelo simple, sin coordinación, latencia interna mínima. Alcanza para un prototipo o una herramienta interna. El techo llega por cuatro lados. La máquina más grande existe y es carísima. La latencia geográfica no se arregla con más RAM. Cada upgrade es downtime. Y hay un SPOF: si ese proceso muere, el negocio muere.

Mitigación, todas implican distribuir: replicar el servicio, balancear carga, poner nodos cerca del usuario o un CDN para lo estático, y actualizar de a poco en lugar de bajar todo.

Métricas

La latencia es cuánto tarda una operación. Se mira en percentiles. p50: la mitad de los requests son más rápidos. p95: solo el 5 % es más lento. p99: la cola. Netflix y Amazon optimizan esto, no el promedio.

EjemploPromedio 100 ms, p99 de 5 s. El informe dice “estamos bien”. Uno de cada cien clicks espera 5 segundos, y en un checkout eso es un carrito abandonado. La latencia que el usuario recuerda es la peor de su sesión.

El throughput es trabajo por unidad de tiempo: requests por segundo, transacciones, MB/s. Depende del hardware, del código, de la concurrencia y del cuello de botella. Un sistema puede ir bien con poca carga y colapsar cuando sube.

El tiempo de respuesta percibido va del click a la pantalla lista: red, servidor, render y terceros. Menos de 100 ms se siente instantáneo. Menos de 1 s mantiene la atención. Más de 10 s, el usuario se va.

Ley de Little: L = λ × W. Si entran 10 requests por segundo y cada uno tarda 0,2 s, en el sistema hay en promedio 2 requests. Si la carga sube y la capacidad no, el tiempo crece. Cerca del límite, la latencia no sube lineal: explota. Un sistema rápido con 5 % de error es peor que uno más lento y confiable.

En la práctica se sube vertical hasta que duele y después se sale horizontal. Scale-out no es “más simple” ni “sin cambios de arquitectura”. Exige pensar la aplicación como distribuida.

Stateless: el request trae todo. Cualquier nodo lo atiende. Sumar nodos suma capacidad. Stateful: el nodo recuerda algo entre requests. Hay que clavar al usuario en el mismo nodo (sticky, IP-hash) o replicar el estado. La regla es dejar stateless todo lo posible y aislar el estado en Redis o en la base.

EjemploDuplicar el catálogo es sumar instancias detrás del balanceador. Duplicar “la sesión que vive en la memoria del server 2” no: ese usuario queda pegado a una máquina que puede morir.

Balanceo. Capa 4 mira TCP y es rápida. Capa 7 mira HTTP y puede rutear por URL, header o cookie. Estrategias: round-robin, least-connections, weighted, IP-hash. Sin health checks, el balanceador sigue mandando tráfico a un nodo muerto. NGINX, HAProxy, un balanceador de nube.

Modelos, y cuándo

Cliente-servidor. El cliente pide, el servidor responde. Simple, datos centralizados, SPOF. MVP y apps internas.

N capas. Presentación, negocio, acceso a datos, persistencia. Cada capa habla con la vecina. Testeable. Puede convertirse en un monolito que solo escala vertical.

P2P. No hay servidor. Cada nodo ofrece y consume. Sin SPOF, y gobernarlo es difícil. BitTorrent, blockchain.

SOA. Servicios reutilizables, en general SOAP sobre un ESB. El bus se vuelve el nuevo SPOF. Es el antecedente pesado de los microservicios.

Microservicios. Un servicio, un bounded context, su propia base, su deploy, su equipo. Hablan REST, gRPC o eventos. Beneficio: escalar solo pagos el Cyber Monday, y que un fallo de recomendaciones no tumbe el catálogo. Costo: latencia de varios saltos, consistencia entre bases, debugging distribuido, y CI/CD maduro como condición.

FowlerNo arranques en microservicios. Llegá cuando el monolito duela. No distribuyas hasta que duela.

Event-driven. Alguien publica “OrdenCreada”. Quien quiera, se suscribe. Acoplamiento muy bajo y buen throughput. Nadie es dueño del flujo completo: debuggear duele. Hace falta un broker de verdad.

Serverless. Una función, un trigger, el proveedor escala de cero a miles y se cobra por uso. Cold start, vendor lock-in, ejecución acotada, debugging más opaco. Sirve para carga irregular, no para un proceso largo con estado.

Cómo se hablan

Síncrono: el emisor espera. Fácil de leer. Si pagos está caído, el checkout se bloquea. Usalo cuando el usuario está mirando la pantalla. Asíncrono: deja el mensaje y sigue. Mejor throughput y resiliencia. Usalo para el mail y las recomendaciones.

RPC hace parecer local una llamada remota. El peligro es olvidar que la red existe. gRPC es la forma moderna: contrato .proto y protobuf binario, muy eficiente entre servicios. REST (Fielding): recursos con URI, verbos HTTP, JSON, servidor sin sesión. Universal en el browser. El contrato es informal salvo OpenAPI. El payload es más gordo.

Cola: un mensaje, un consumidor. Reparte trabajo. Pub/sub: un evento, muchos suscriptores. RabbitMQ enruta colas de trabajo. Kafka es un log persistente de altísimo throughput: el evento queda. Garantía habitual: at-least-once. Puede llegar dos veces. La idempotencia es de la aplicación.

El API gateway es la única puerta: enruta, autentica, limita, termina TLS. Si le metés reglas de negocio, se vuelve un monolito. El BFF es un gateway por tipo de cliente: el móvil pide un payload chico, la web pide la ficha completa. Service discovery: las direcciones cambian. Hardcodear una IP es creer que la topología no cambia.

GoF en este contexto. Proxy: el gateway y el stub de gRPC. Adapter: envolver una API vieja. Observer: la base de publicar y suscribir. Strategy: cambiar backoff o el algoritmo de balanceo. Facade: el BFF. Decorator: auth, logging y tracing alrededor del handler.

Las 8 falacias de Deutsch

Creer cualquiera de estas produce software que anda en la notebook y se cae en producción.

  1. La red es confiable. Se corta. Sin timeout ni retry, el cliente se cuelga.
  2. La latencia es cero. Quince llamadas sync entre servicios suman quince idas y vueltas.
  3. El ancho de banda es infinito. Un catálogo de 20 MB de JSON no escala.
  4. La red es segura. Sin TLS y sin auth, cualquiera en el medio lee el token.
  5. La topología no cambia. Una IP fija se rompe cuando el proceso se mueve.
  6. Hay un solo administrador. El DNS lo toca otro equipo. El certificado lo rota otro.
  7. El costo de transporte es cero. Sacar datos de una región, y un log gigante, se pagan.
  8. La red es homogénea. No todos hablan el mismo protocolo ni tienen el mismo MTU.
Trampa“Los servidores tienen memoria infinita” no es una falacia de Deutsch.

Fallos, CAP y orden

Crash: el nodo se detiene. Omission: pierde mensajes. Timing: responde tarde. Byzantine: miente o manda datos corruptos. Diseñá para fallos parciales frecuentes, no para un apagón total raro.

CAP. Ante una partición no podés tener a la vez consistencia fuerte (todos leen el último write) y disponibilidad (todo request recibe respuesta). La partición no se elige: la red se parte. Durante la partición elegís C o A.

CPUn banco: si la réplica de Córdoba no ve la de Buenos Aires, el débito responde error, no un saldo viejo que deja extraer dos veces.
APUn like, el DNS, Cassandra, DynamoDB: se responde con un dato que puede estar atrasado y se converge cuando la partición sana. Un like tarde es aceptable. Un asiento de avión vendido dos veces, no.

Consistencia eventual: si dejan de llegar escrituras, todos los nodos llegan al mismo valor. Diseñar distribuido es decidir qué inconsistencia tolerás.

No hay un “ahora” común. Los relojes físicos, aun con NTP, derivan. Happened-before (Lamport, 1978): A → B si ocurren en el mismo proceso y A fue antes; si A es el envío y B la recepción; o por transitividad. Si no hay esa cadena, son concurrentes. El reloj lógico incrementa un contador; al recibir, hace max(local, recibido) + 1. Si A causó B, el reloj de A es menor. La vuelta no vale: un número menor no prueba la causa. El reloj vectorial detecta concurrencia cuando los vectores no son comparables. El vector crece con la cantidad de nodos.

ACID no cruza servicios

Atomicidad, consistencia, aislamiento y durabilidad alcanzan dentro de una base. Con una base por servicio no hay transacción global. BASE: basically available, soft state, eventual consistency.

2PC. El coordinador pregunta “¿pueden commitear?”. Si todos dicen sí, commitea. Si uno dice no, rollback. Los participantes quedan lockeados. Si el coordinador cae entre las dos fases, quedan bloqueados. Por eso a escala se abandonó.

Saga. Una secuencia de transacciones locales. Cada paso tiene una compensación. Si el paso 3 falla, se deshacen 2 y 1. No es atómico: durante un rato el mundo está a medias.

Compra, orquestada por Órdenes1. Reservar stock. Si falla, se cancela. 2. Cobrar. Si falla, se libera el stock. 3. Confirmar. Si falla, reembolso y se libera el stock. 4. Notificar, best-effort: un mail perdido no deshace la compra. En coreografía no hay director: cada servicio escucha y publica. Sirve para pocos pasos. La orquestación se debuggea y puede volverse cuello de botella.

CQRS. El modelo de escritura no es el de lectura. El comando valida y no devuelve la pantalla. La query lee un modelo desnormalizado, a veces otra base. Las lecturas escalan aparte. Durante un momento, la búsqueda no muestra lo que acabás de guardar. Usalo cuando las lecturas superan por mucho a las escrituras.

Event sourcing. No guardás {A, B}. Guardás AgregadoA, AgregadoB, RemovidoA. El estado es reproducir los eventos. Hay auditoría y viaje al pasado. Migrar el formato de un evento duele. Los snapshots evitan reejecutar miles de hechos.

Idempotencia. Hacerlo N veces equivale a hacerlo una. Sin una idempotency-key, el retry de pagos cobra dos veces. Se guarda el id ya procesado. PUT y SET pisan. POST e INCREMENT no.

Resiliencia

Un fallo local no tiene que ser una caída general. El orden mental es timeout, retry con criterio, circuit breaker, bulkhead, fallback.

Timeout. Toda llamada remota tiene techo. Elegilo cerca del p99 real, no el default del framework, que a veces es infinito. La capa de afuera espera más que la de adentro. Sin timeout, un servicio lento se come todos los hilos del cliente.

Retry. Solo errores transitorios (timeout, 5xx), nunca un 400. Backoff exponencial (1 s, 2 s, 4 s), jitter para que todos no reintenten juntos, tope de 3 a 5. Retry inmediato sobre un servicio caído es una tormenta.

Circuit breaker. Closed: las llamadas pasan y se cuentan los fallos. Open: se superó el umbral (por ejemplo más del 50 % en 30 s); las llamadas ni salen. Half-open: pasado un tiempo se dejan pasar unas pruebas. Si responden, vuelve a closed. Si fallan, vuelve a open. El retry insiste. El breaker deja de insistir.

Bulkhead. Compartimentos del barco. Un pool de hilos para pagos y otro para el catálogo. Si pagos se cuelga, el home sigue.

Rate limiting. Token bucket deja ráfagas. Leaky bucket aplana. Al pasar el límite: HTTP 429 y Retry-After.

Fallback. Degradar, no romper. Recomendaciones caídas → “los más vendidos” cacheados. Reviews lentas → se oculta la sección. Siempre se loguea.

Health checks. Liveness: ¿el proceso está vivo? Readiness: ¿puede recibir tráfico? Startup: ¿terminó de arrancar? Un check que valida demasiadas dependencias puede tumbar al servicio que quiere cuidar.

Pagos externoTimeout 3 s, 3 retries con backoff y jitter, breaker si falla más del 50 % en 30 s, fallback que encola el cobro y le dice al usuario “estamos procesando el pago”. Recomendaciones: si pasan de 500 ms, se oculta el bloque. Bulkhead para que los hilos de pagos no se coman los del catálogo.

Contenedor contra VM

Una VM virtualiza hardware. Trae sistema operativo completo. Aislamiento fuerte, gigabytes, minutos en arrancar. Un contenedor comparte el kernel del host y se aísla con namespaces y cgroups. Megabytes, segundos. La imagen es inmutable: app + dependencias + runtime. El Dockerfile es la receta. El registry la distribuye. Docker (2013) no inventó los contenedores: los hizo usables. En el pipeline esa imagen se construye una vez, se tagea con el hash del commit (nunca latest en producción) y se promueve. Un multi-stage build deja el SDK afuera: la imagen final solo lleva el binario.

TrampaUn contenedor no incluye un sistema operativo completo. Eso es la VM.

UML y C4, lo justo

CASE: herramientas de análisis, diseño y documentación. En distribuido alcanzan pocos diagramas. Componentes: quién depende de quién. Despliegue: en qué nodo corre cada cosa. Secuencia: qué pasa en el tiempo cuando el usuario compra; ahí se ve dónde hace falta un timeout o una saga.

C4. Contexto: el sistema como caja, para cualquiera. Contenedores: apps, bases y colas desplegables. “Container” en C4 no significa Docker: significa unidad desplegable. Componentes: módulos dentro de una app. Código: casi siempre de más. PlantUML y Mermaid viven en el repo. Un dibujo suelto se pudre.

Checkpoint

El p99 de pagos se disparó y los hilos del checkout están bloqueados. ¿Qué tres patrones aplicás, y en qué orden de diseño?

Timeout para no esperar para siempre, circuit breaker para dejar de llamar cuando está degradado, fallback para encolar el cobro y responder. El retry solo con backoff, y un bulkhead para que el catálogo siga teniendo hilos.

¿Por qué una saga no es 2PC con otro nombre?

2PC busca atomicidad y lockea a todos hasta el final. La saga hace transacciones locales y compensaciones. Durante un rato el stock está reservado y el pago no: hay que tolerar ese intermedio.

Unidad 3 · Humble, Farley, DORA

Integración y entrega continua

El cycle time es el tiempo entre que se decide un cambio y ese cambio está en manos del usuario, de forma repetible. La pregunta de Humble: ¿cuánto tarda tu organización en poner en producción una línea, y puede hacerlo otra vez igual? Tradicional: semanas. Moderna: horas. Elite: minutos, cientos de deploys por día.

Importa porque una feature que no está en producción no genera valor, el feedback de usuarios reales llega antes, un release chico falla menos y se revierte fácil, y el equipo deja de pasar el sábado a las 3 a.m. Un release grande concentra el riesgo de todo lo que se acumuló por miedo a desplegar.

Las dos situaciones de la claseLa demo de mañana: el código compila, pero armar el entorno lleva dos días. El hotfix de una línea: el último release tomó un fin de semana y quien lo hizo renunció. Las dos son el mismo problema: la entrega no está bajo control.

Cuatro antipatrones

1. El día de release es un evento. Se prepara el entorno a mano, se copian artefactos, se prende pieza por pieza. El equipo le teme, releasea menos, cada release es más grande, duele más.

2. Despliegue manual. Un documento de 15 páginas, se llama al desarrollador a mitad del deploy, “en staging andaba”, resultado impredecible. El mito “lo manual es más auditable” es falso: un script versionado deja un log de cada paso. La alternativa son dos gestos: elegir la versión y apretar desplegar.

3. No probar en un entorno parecido a producción. QA vio la app en la notebook. Operaciones la ve el día del release. Cuanto más distintos son dev y prod, más sorpresas. El deploy también se prueba, todo el tiempo. La misma imagen ayuda.

4. Configuración a mano en producción. SSH, un cambio “chiquito”, y el nodo 2 ya no es igual al nodo 1: drift. No hay rollback de esa config. La alternativa es Infrastructure as Code: Terraform, CloudFormation, Bicep, Ansible, Pulumi. Volver atrás es aplicar el commit anterior.

Principios de Humble y Farley

La diapositiva dice 7 y lista 8. Escribilos con un ejemplo al lado.

  1. Proceso repetible y confiable. Releasar es apretar un botón porque ya se hizo cientos de veces. Si hace falta “el que sabe las mañas”, no es repetible.
  2. Automatizar casi todo. Provisioning, instalación, configuración, validaciones. No se automatizan la exploración manual ni una aprobación de compliance. Si lo hiciste tres veces a mano, es candidata.
  3. Todo bajo control de configuración. Código, scripts, IaC, config, migraciones, documentación. Prueba de fuego: un dev nuevo clona, un comando compila, un comando despliega. El build se identifica por hash, versión y configuración.
  4. Si duele, hacerlo más seguido. Integrar duele → integrar en cada commit. Releasear duele → releasear a un entorno como prod todos los días, en chico.
  5. Build quality in. Encontrar el bug en QA es tarde: el defecto ya está en el producto. TDD, pair, review, análisis estático, unitarios en CI. Testing no es una fase final.
  6. DONE significa RELEASED. Nivel 1, débil: compila y los tests pasan. Nivel 2: corre en un entorno como prod. Nivel 3: está en producción. Nivel 4: un usuario real obtiene valor.
  7. Todos son responsables del release. Dev, QA y ops ven el mismo pipeline. “Yo programo, ellos despliegan” reparte la culpa y nadie es dueño.
  8. Mejora continua. PDCA: planear, hacer, medir, estandarizar o ajustar. Retrospectiva del proceso de entrega. Se miden cycle time, defectos que se escapan y MTTR.
No es un principio“Deployar menos para reducir el riesgo”. El riesgo baja con releases chicos y frecuentes.

Feedback e integración continua

Tres condiciones, las tres. Todo cambio dispara feedback: código, configuración, sistema operativo, un sistema externo. Llega rápido: un reporte de tres días no corrige el commit de hoy. El equipo actúa: un build rojo ignorado entrena al equipo a ignorar el siguiente.

Costo empírico de la cátedra: al escribir el código, 1×. En el commit, 2–5×. En QA, 10×. En staging, 30×. En producción, 100×. Se pierde el contexto, hay que coordinar equipos, y el usuario ya lo sufrió.

CI la definió Kent Beck dentro de XP (1999) y la popularizó Fowler (2006). Cada desarrollador integra a la rama principal al menos una vez al día. Cada integración se buildéa y se testea sola. El build roto se arregla ya. Sin CI, el software está roto hasta que alguien demuestra lo contrario, y la fase de integración del final es una caja negra.

Tres prerrequisitos. Si falta uno, la herramienta no lo tapa: VCS con código, config, scripts, tests e IaC; build automatizado de un solo comando; compromiso del equipo. Comprar un servidor no es adoptar CI.

  • Check-in frecuente al trunk, dos veces al día o más. “Termino la feature de tres semanas y después mergeo” es el antipatrón.
  • Arreglar el build ya. Time-box de 10–15 minutos y, si no entra, revert. No se comentan tests para que pase. No se va a casa con el build rojo.
  • Tests locales antes del push. Pull, build, tests, commit, push, mirar el servidor, arreglar o revertir.
  • TDD: red, green, refactor. Los tests escritos después suelen probar la implementación, no el comportamiento.

El servidor (Jenkins, GitHub Actions, GitLab CI, Azure Pipelines) dispara el workflow. El YAML vive en el repo. CI es el piso, no el techo.

Release candidate y el binario único

Un RC es un build que podría ir a producción. El modelo viejo lo fabrica al final, con code freeze y semanas de QA. Cada RC concentra riesgo. El modelo de la materia: cada commit que pasa el pipeline es un RC. Hace falta una suite automatizada, un pipeline determinístico y ambientes parecidos a prod.

El artefacto dice de qué commit salió, con qué dependencias y qué corrida del pipeline. Se construye una sola vez. El binario de prod es el mismo que pasó los tests. Recompilar en cada ambiente mete entropía: una dependencia que se movió, un latest que cambió. Antipatrón de DZone: el software se reconstruye en cada etapa.

Promoción: commit → artefacto v1.2.3-abc123 en un registry → dev → QA → staging → prod. Cambia la configuración, no el binario. En Continuous Delivery, lo único extra es la aprobación.

CI, Delivery, Deployment

Qué automatizaQué sigue siendo humano
Continuous IntegrationCompilar y testear cada commit. El artefacto queda construido.Decidir el release y desplegar.
Continuous DeliveryEl pipeline hasta un artefacto probado, desplegable con el mismo mecanismo.El push a producción: un botón de aprobación.
Continuous DeploymentTambién el deploy a producción, si los gates pasan.Nada en el camino del commit al usuario.
La fraseLa diferencia entre Delivery y Deployment no es “usa contenedores” ni “es solo para SaaS”. Es si un humano autoriza producción. Un banco puede vivir en Delivery por compliance y ser excelente. Decir que Delivery “despliega solo” es falso.

El deployment pipeline

Humble y Farley: la manifestación automatizada del proceso que lleva el código desde el VCS hasta el usuario. Cada cambio lo dispara. Es visible para dev, QA, ops y negocio. Es un pull system: el tester se despliega a su ambiente, ops promueve a prod, nadie espera un ticket al “equipo de build”.

  1. Commit stage. ¿Funciona a nivel técnico? Compila, unitarios, linter, empaqueta y publica. Menos de 10 minutos, idealmente 5. Si falla, no hay integración.
  2. Aceptación automatizada. Integración, end-to-end, contratos, escenarios de negocio, en un ambiente parecido a prod. Tarda minutos.
  3. No funcionales. Capacidad, stress, soak, seguridad (SAST/DAST), performance. k6, JMeter, Gatling, OWASP ZAP. Van tarde para no frenar el feedback.
  4. Manual / UAT / exploratorio. Usabilidad y casos que un assert no ve. En Delivery puede ser antes de prod. En Deployment ocurre después, acotado por feature flags.
  5. Release. El mismo script que en los otros ambientes. Cambia la config de prod. El rollback es un botón: el artefacto anterior. Si el rollback es un proyecto, el release va a dar miedo.

Prácticas: construir una sola vez; el mismo deploy en todos los ambientes; smoke test después de cada deploy (health 200, login, en menos de un minuto; si falla, rollback); desplegar sobre una copia de producción; si algo falla, el pipeline se detiene y avisa.

Estrategias de release

El objetivo es achicar el blast radius: cuánta gente sufre si este cambio está mal.

Recreate. Se baja todo lo viejo y sube lo nuevo. Hay downtime. Sirve en dev. No sirve en un checkout.

Rolling. Instancia por instancia. Siempre hay algo atendiendo. Dos versiones conviven, así que el esquema de datos tiene que ser compatible hacia atrás y hacia adelante. Si el bug aparece en la instancia 4, ya hay usuarios en la versión nueva.

Blue-green. Dos entornos. Blue atiende. Green recibe la versión nueva, se calienta, smoke tests. El balanceador cambia de golpe. Rollback: volver a apuntar a blue. Cuesta el doble de infra durante la ventana. Una migración irreversible lo complica.

Canary. 1 %, después 5, 25, 50, 100, mirando errores, latencia y una métrica de negocio. Si el p99 se dispara, el porcentaje vuelve a 0.

Feature flags. Separamos deploy de release. El código ya está en prod y apagado. Fowler: release toggles (feature incompleta), experiment toggles (A/B), ops toggles (kill switch), permission toggles (un segmento). Apagar el flag es más rápido que un redeploy. Habilitan trunk-based. La deuda es el flag que nadie borra.

Progressive delivery las combina: deploy con el flag apagado, encendido para el equipo, después 1 % de usuarios, después todos, y en el release siguiente se borra el flag.

El descuentoEntra por rolling con el flag apagado. Se enciende para empleados. Después canary al 5 %. La conversión cae: se apaga el flag en segundos, sin revertir la imagen. El binario que corre es el mismo que pasó staging.

Rollback: rápido, automático y ensayado. Redeploy de la versión anterior, switch del balanceador, canary a 0, o flag apagado. El esquema de la base se diseña compatible con la versión previa.

Ambientes, 12-Factor, secretos, IaC

Ambientes: local, dev, QA, staging, producción. Cada uno se parece al siguiente. El artefacto es el mismo. Solo cambia la config.

Twelve-Factor (Heroku, 2011). El parcial cita el principio 3 y a veces el conjunto. 1) una codebase, muchos deploys. 2) dependencias explícitas. 3) config en el entorno, no en el código. 4) bases y colas como recursos adjuntos. 5) separar build, release y run. 6) procesos stateless. 7) exponer por un puerto. 8) escalar con más procesos. 9) arranque rápido y apagado limpio. 10) paridad dev/prod. 11) logs como stream. 12) tareas de admin de una sola corrida.

TrampaGuardar la connection string en el repo es el antipatrón. 12-Factor dice lo contrario.

Secretos. Nunca en el repo. Vault, Secrets Manager, Key Vault. Rotación, mínimo privilegio, auditoría, y un scan por si alguien los commiteó. Base64 no es cifrado.

SemVer. MAJOR rompe compatibilidad. MINOR agrega sin romper. PATCH corrige. Conventional commits: feat sube minor, fix sube patch, BREAKING CHANGE sube major.

IaC. La infraestructura es código revisable, reproducible y reversible. El código es la documentación. El antipatrón 4 (config a mano) se cierra acá.

Gates, observabilidad, DORA

Un gate que no bloquea es un comentario: compila, unitarios, cobertura del código nuevo, análisis estático, scan de dependencias y de la imagen, e2e, performance dentro del umbral. En Delivery, la aprobación humana tiene sentido por regulación o por un lanzamiento. Tiene que ser un botón con contexto y registro de quién aprobó.

Después del deploy se mira. RED para el servicio: rate, errors, duration en percentiles. USE para el recurso: utilization, saturation, errors. OpenTelemetry correlaciona métricas, logs y trazas. Si el error sube 2 puntos contra el baseline, o el p99 sube 50 %, rollback. El equipo que desplegó mira esa ventana.

Post-mortem blameless: línea de tiempo, impacto, cinco porqués, acciones. El incidente tiene que dejar el sistema mejor.

DORA (Forsgren, Humble, Kim, Accelerate, 2018). Cuatro métricas. No son un examen para sacar 10: diagnostican.

EliteHighMediumLow
Deployment frequencyVarias al díaDiaria a semanalSemanal a mensualMenos de una cada 6 meses
Lead time for changes< 1 día1 día a 1 semana1 semana a 1 mes> 6 meses
Change failure rate0–15 %16–30 %16–30 %16–30 %
MTTR< 1 hora< 1 día1 día a 1 semana> 6 meses

Frecuencia y lead time miden velocidad. Change failure rate y MTTR miden estabilidad. Lead time for changes va del commit al código en producción. MTTR va del inicio del incidente a la restauración, no hasta el post-mortem. La creencia que el libro desmiente: ir más rápido no obliga a ser más frágil. Los elite son frecuentes y se recuperan en menos de una hora. Los low performers son lentos y frágiles a la vez.

TrampaUptime, latencia, throughput y error rate son métricas del servicio (parecidas a RED), no DORA. Velocity y burndown tampoco.

SPACE complementa: Satisfaction, Performance, Activity, Communication, Efficiency. Nunca una sola métrica de productividad. Commits o líneas como objetivo disparan la ley de Goodhart.

CI/CD como capacidad son tres patas: tecnología (VCS, CI, registry, observabilidad), procesos (done, gates, rollback) y cultura (el que lo construye lo opera, post-mortem sin culpa, confianza en el verde). Sin cultura, las herramientas no se usan. Sin herramientas, la cultura se agota.

Checkpoint

El equipo dice “hacemos continuous delivery” porque Jenkins despliega a producción en cada verde. ¿Qué están haciendo en realidad?

Continuous Deployment. Delivery automatiza hasta dejar el artefacto listo y deja la autorización de producción en una persona.

¿Por qué recompilar la imagen en staging “para estar seguros” empeora el release?

El binario de producción deja de ser el que pasó los tests. Una dependencia puede haber cambiado. Se promueve el mismo artefacto y solo cambia la configuración.
